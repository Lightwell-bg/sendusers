# Расписание и очередь отправки кампаний

Дата: 2026-09-08

## Зачем

Сейчас у кампании есть только «отправить прямо сейчас» (кнопка «Подтвердить
отправку»). Ничто не мешает случайно запустить две отправки одновременно —
это бьёт по лимитам Telegram (оба потока идут одному и тому же боту) и
затрудняет мониторинг. Нужно: (1) возможность назначить кампании время
отправки заранее, (2) гарантия, что кампании не отправляются параллельно —
только строго одна за другой, в порядке времени.

## Ключевые решения

- **Очередь = «строго одна за другой»**, а не просто список независимых
  расписаний. Никогда не идут две отправки одновременно.
- **Dry-run обязателен заранее.** Планировать можно только кампанию в
  статусе `ready` (dry-run уже пройден) — так же, как сейчас работает ручная
  отправка.
- **После рестарта сервиса просроченное не досылается само.** Если кампания
  должна была уйти, пока сервис лежал, — она не стартует автоматически при
  подъёме; ждёт ручного решения администратора. Кампания, ставшая
  просроченной, пока сервис работал и очередь была занята другой отправкой —
  это нормальный сценарий, досылается сама.
- **Ручная отправка и «Продолжить» после паузы тоже встают в очередь.**
  Единый механизм: «отправить сейчас» технически = «запланировать на текущее
  время», через тот же фоновый обработчик очереди. Никаких отдельных путей
  запуска в обход очереди.
- **Dry-run в сериализацию не входит** — может идти параллельно с активной
  отправкой другой кампании (он не шлёт сообщения массово, только проверяет
  членство в чатах).
- **Порядок очереди определяется только временем.** Ручной перестановки
  (drag&drop/стрелки) нет — чтобы передвинуть кампанию, меняешь её время.
  Снять с расписания можно в любой момент (возврат в `ready`).
- **UI** — отдельная страница «Очередь» в навигации.

## Модель данных

### `campaigns.scheduled_at`

Новая колонка, `TEXT`, nullable, UTC (тот же формат, что и остальные
временные поля, `_now()` в `db.py`). Мягкая миграция в `_migrate()`, как уже
сделано для `image_path`.

### Новый статус: `scheduled`

Расширяется существующая машина состояний:

```
draft → dry_running → ready → scheduled → running → done/failed/cancelled
                         ↑         │
                         └─────────┘ (unschedule)
                    paused → scheduled → running
```

- `ready → scheduled` — постановка в расписание (`schedule_campaign`).
- `scheduled → scheduled` — смена времени у уже запланированной (тот же
  переход, только обновляется `scheduled_at`; не путать со сменой статуса).
- `scheduled → ready` — снятие с расписания (`unschedule_campaign`).
- `scheduled → running` — забирает фоновый обработчик очереди, когда
  подходит время и очередь свободна.
- `paused → scheduled` — «Продолжить» теперь тоже сначала планирует «на
  сейчас», а не переводит в `running` напрямую.
- `scheduled → cancelled` — через существующий `/cancel`, расширяем список
  разрешённых исходных статусов.
- `ready/paused → scheduled` (мгновенно, `scheduled_at = now`) — то, что
  раньше было прямым `/send` (и «Подтвердить отправку» из `ready`, и
  «Продолжить» из `paused`, оба теперь идут через эту же постановку в
  очередь, а не напрямую в `running`).

`STATUS_LABELS`/`STATUS_CLASS` в `main.py` — добавить `scheduled` (бейдж,
например, `badge-blue`, метка «Запланирована»).

## Фоновый обработчик очереди (`worker.py`)

Асинхронный цикл, тикает каждые ~5 секунд (константа, настраиваемая по
аналогии с остальными интервалами в `config.py`, но без необходимости
выносить в `.env` — не пользовательский параметр, а внутренний тик).
Запускается один раз при старте (`resume_on_startup`, рядом с уже
существующим подхватом `running`/`dry_running` кампаний).

На каждом тике:

1. Если прямо сейчас есть кампания в статусе `running` (проверка через
   `db.campaigns_in_status(("running",))` или через уже существующий
   `_tasks`) — ничего не делать, ждать следующего тика.
   Действующая гарантия одиночного `uvicorn`-процесса и атомарный
   `transition_campaign` уже защищают от двойного старта — обработчик
   очереди работает поверх них, а не вместо.
2. Иначе — выбрать среди кампаний в статусе `scheduled` ту, у которой
   `scheduled_at <= now()` и `scheduled_at >= process_start_time`,
   с наименьшим `scheduled_at` (при равенстве — наименьший `id`).
   `process_start_time` — время, зафиксированное один раз при старте
   процесса (переменная модуля `worker.py`, аналог `_tasks`).
3. Если такая кампания нашлась — вызвать `start_send(campaign_id)` (уже
   существующая функция, делает атомарный переход в `running` и
   регистрирует таск).
4. Кампании, у которых `scheduled_at < process_start_time` (просрочены ещё
   до старта процесса), обработчик не трогает вообще — остаются в
   `scheduled`, видны на странице очереди с пометкой «Просрочено».

Условие в шаге 2 одинаково корректно обрабатывает оба ранее обсуждённых
случая: кампания, ставшая due, пока сервис работал и очередь была занята
(её `scheduled_at` всё ещё `>= process_start_time` — стартует, как только
освобождается), и кампания, просроченная ещё до старта сервиса (не
стартует, ждёт админа).

### Новые функции в `worker.py`

- `async def schedule_campaign(campaign_id, scheduled_at) -> bool` —
  переход `ready → scheduled` или обновление времени внутри `scheduled`;
  `False`, если кампания не в одном из этих статусов.
- `async def unschedule_campaign(campaign_id) -> bool` — `scheduled → ready`.
- Изменение `start_send`: раньше он атомарно переводил статус из
  `("ready", "paused")` в `running` и сразу планировал фоновую задачу.
  Теперь единственный, кто зовёт `start_send` напрямую — обработчик очереди,
  и на входе у кампании уже статус `scheduled` — поэтому список разрешённых
  исходных статусов в переходе меняется с `("ready", "paused")` на
  `("scheduled",)`. Роуты `/send` (и «Продолжить») теперь вызывают
  `schedule_campaign(id, now())`, а не `start_send` напрямую.
- Фоновая задача-тикер: `async def _queue_processor() -> None`, запускается
  через `asyncio.create_task` в `resume_on_startup` (или в `lifespan`
  `main.py`, рядом с `await worker.resume_on_startup()`), крутится, пока жив
  процесс.

## Роуты (`main.py`)

- `POST /campaigns/{id}/schedule` — форма: `scheduled_at` (ISO-строка в
  UTC, см. ниже про таймзону), csrf. Работает из `ready` и `scheduled`.
- `POST /campaigns/{id}/unschedule` — csrf. Работает из `scheduled`.
- `POST /campaigns/{id}/send` — без изменений сигнатуры, но внутри теперь
  зовёт `worker.schedule_campaign(id, now())` вместо `worker.start_send`.
  Работает из `ready` **и** `paused` (сохраняем текущее поведение кнопки
  «Продолжить» — тот же роут).
- `POST /campaigns/{id}/cancel` — добавить `scheduled` в список статусов,
  из которых разрешена отмена.
- `GET /queue` — список кампаний со статусом `scheduled`, отсортированный
  по `scheduled_at` (потом `id`), плюс сверху — текущая `running`-кампания,
  если есть (для контекста «что сейчас идёт и почему остальные ждут»).

### Таймзона

Поле времени в форме — `<input type="datetime-local">`, значение в нём —
локальное время браузера. Перед отправкой формы конвертируется в UTC ISO
небольшим JS (`new Date(value).toISOString()`) в скрытое поле — админ вводит
своё время, не пересчитывает вручную в серверное (VPS работает в UTC).

## UI

### Страница «Очередь» (`templates/queue.html`)

Таблица: время (локальное — конвертировать обратно из UTC в браузере или
показать как есть с пометкой UTC — решить при реализации, не принципиально),
название, боты, статус («Ждёт своего часа» / «Просрочено»), кнопки
«Отправить сейчас» / «Изменить время» / «Снять с расписания» / «Открыть».
Ссылка в навигации `base.html` рядом с «История».

### Карточка кампании (`campaign_detail.html`)

- Статус `ready`: к существующим кнопкам (Dry-run заново, Тест себе,
  Редактировать, Подтвердить отправку) добавляется поле даты/времени +
  кнопка «Запланировать».
- Статус `scheduled`: показывает запланированное время; кнопки «Отправить
  сейчас», «Изменить время» (то же поле + кнопка «Запланировать», уже с
  текущим значением), «Снять с расписания», «Отмена».
- Статус `paused`: кнопка «Продолжить» остаётся текстуально такой же —
  пользователю не нужно знать, что под капотом она тоже идёт через очередь
  (разве что почти всегда стартует мгновенно, т.к. очередь обычно свободна).

## Что не меняется

- `/campaigns/{id}/edit` — как и сейчас, доступен только из `draft`/`ready`;
  запланированную кампанию нельзя редактировать текст, пока не снята с
  расписания (естественное следствие текущей проверки статуса, менять не
  нужно).
- Dry-run — без изменений, не входит в сериализацию.
- At-most-once доставка, реестр `_tasks`/`_control`, резюме после рестарта
  для уже `running` — без изменений, обработчик очереди работает поверх.

## Тестирование

`tests/test_db.py`:
- миграция добавляет `scheduled_at` к старой схеме (как тест на
  `image_path`);
- запрос кампаний в `scheduled`, готовых к запуску, сортировка по времени.

`tests/test_worker.py`:
- две кампании запланированы на одно и то же время — отправляются строго
  по очереди, не параллельно;
- кампания, просроченная **до** старта процесса (`scheduled_at` раньше
  `process_start_time`) — не стартует сама при `resume_on_startup`, статус
  остаётся `scheduled`;
- кампания становится due, пока очередь занята другой отправкой — стартует
  сама сразу после освобождения;
- ручная отправка (`schedule_campaign(id, now())`) не стартует мгновенно
  в обход очереди, если уже что-то отправляется — ждёт;
- «Продолжить» из `paused` идёт тем же путём (через `scheduled`), не
  напрямую в `running`.

`tests/test_routes_main.py` (или новый файл):
- `POST /schedule` переводит `ready → scheduled`, `GET /queue` показывает
  кампанию;
- `POST /unschedule` возвращает в `ready`;
- `POST /cancel` работает из `scheduled`.

  для отображения в браузере через JS (аналогично полю ввода) — чтобы не
